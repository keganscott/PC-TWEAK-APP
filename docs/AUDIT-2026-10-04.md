# PeakTweaks audit and game plan (2026-10-04)

Scope: all of `crates/engine`, `crates/field-check`, `src-tauri`, `src` (UI), `e2e`, `e2e-tauri`, `scripts`, CI, against `docs/PEAKTWEAKS_DEV_PLAN.md` and `docs/NOTES.md`. Branch head `f20a184`.

## 1. Bottom line

1. **The safety core is in good shape.** Every registry write goes through the journal with backups first; undo, crash recovery, the protected data folder, IPC boundary and "no network" are built and were green on Windows CI (last green run 37089359799). No unwrap/panic paths in production code, 0 npm vulnerabilities, 329 Rust + 42 UI + 14 browser tests pass locally.
2. **A real user cannot change anything yet.** The release build runs on the Free licence, both catalogue tweaks are Pro-only, and the second one (Fortnite priority) is blocked for every game until anti-cheat testing. So today the shipped app scans, makes a restore point, and shows guidance. That is the biggest gap between the code and a product.
3. **The biggest unproven risk is the restore point.** Creating one has never succeeded on a real Windows client (N24): CI runners are Windows Server, which has no System Restore. Every change is gated on it, so if it fails on real PCs nothing works.
4. **Two blockers outside the code:** GitHub Actions is refusing jobs over billing (N58, since 2026-10-03), so nothing after commit `aab3a11` is Windows-verified; and the real-PC field check has never been run.
5. **I found 6 bugs (none in the write path's safety guarantees) and 8 improvements**, listed below with fixes.

## 3. Bugs found

Severity: **M** = wrong behaviour a user will hit; **L** = edge case or misleading record.

| # | Sev | Where | What is wrong | Fix |
|---|---|---|---|---|
| B1 | M | `src/components/views/BackupsView.tsx:33`, `engine.rs:267` | **The restore-frequency change PeakTweaks makes itself is invisible and cannot be undone from the UI on its own.** Making a restore point writes `SystemRestorePointCreationFrequency=0` (an internal tweak). Backups lists only catalogue tweaks, and "Undo all" is disabled while none is applied, so the user never sees this change or a way to undo it. The engine's `revert_all` would undo it. | List internal changes in "Applied now" (engine adds them to the view with a plain name) and enable Undo all whenever the journal has outstanding writes. Consider also undoing the frequency change right after the point is made (needs Kegan's OK: the plan locks "journalled and restorable", not "kept"). |
| B2 | M | `tweaks/mouse_accel.rs:82`, `tweaks/ifeo_priority.rs:127-130` | **A change that someone else undid loses its Undo.** If the user turns acceleration back on in Windows after applying, the state reads "Not applied" although the journal still has the apply outstanding. Tools then offers Apply, Backups does not list it, and its offline undo file stays. | New state `Drifted` (journal says applied, Windows says otherwise): show both "Apply again" and "Undo (restore the original)". |
| B3 | M | `ToolsView.tsx:96`, `engine.rs:302` | **Apply is enabled for Pro changes on the Free plan** and fails only after the click with "needs the Pro plan". The tier check is engine-side (correct), but the view does not know about it in advance. | Engine fills `TweakView.blocked` with `TierRequired` when the licence is too low (same check as `apply`, still enforced there); UI then shows the lock and upgrade text instead of an error. |
| B4 | M | `engine.rs:220`, `store.ts:164,200` | **Every apply, undo, game pick and settings save runs a full fresh probe of the PC** (`audit` → `rescan_fresh`: all WMI hardware queries, a 2-second process sample, disk lookups). It holds the engine lock for seconds, so a quick Undo right after waits behind it. | Split `audit()` (cached) from an explicit "Check again" (`audit_fresh`). After a change, only security and restore state need re-reading. |
| B5 | L | `restore.rs:322` | **The journal says "protection was not turned on by us" even when it may have been.** Protection on/off is always Unknown (N23), and Unknown is recorded as `false`. | Make `protectionEnabledByUs` a three-way value (yes/no/unknown) or drop it until a reliable signal exists. |
| B6 | L | `restore.rs:371` | If Windows does not list our point under the sequence number it gave, verification falls back to "any newer point", which could be another program's point made at the same moment. | Accept the fallback only when its description is ours; otherwise keep retrying, then fail. |

Also noted, not bugs: a failed rollback inside a failed apply is silent (`engine.rs:356`; the change stays undoable, but the UI could say "partly applied, use Undo"). A narrow race in `delete_key_if_empty` (`registry/windows.rs:178`) between the empty check and the delete; it removes only a key with no subkeys, so worst case a value written in that instant is lost.

Fixed during this session before the report: `recover.cmd` accepted profile folders containing `!` or `^`, which it would have mangled (commit 050faf1); the offline undo set missed a change interrupted by a crash until the next commit (f056301). Both are still waiting on Windows CI.

### Step 3. Make the app useful for free users: the Starter fixes (after your approval of new tweaks and N50)

The plan's Starter tier promises "five one-click fixes with undo". Candidates from the plan, and how each fits today's safety machinery:

| Fix | Mechanism | Fits `Transaction` today? | Work |
|---|---|---|---|
| Game on the high-performance graphics chip (laptops) | `HKCU\Software\Microsoft\DirectX\UserGpuPreferences` value per game exe | **Yes** (registry, user hive) | Small: the read side exists (`gpu_choice.rs`); write `GpuPreference=2;` |
| Background recording off (Xbox Game Bar capture) | `HKCU\System\GameConfigStore` and `...\GameDVR` values (VERIFY) | **Yes** | Small |
| Power plan to High performance | `powercfg /setactive` | No: needs a new journal record kind ("previous active scheme") and its revert | Medium: design + DECISIONS entry |
| Refresh rate to the monitor's maximum | `ChangeDisplaySettingsEx` | No: new record kind ("previous display mode"); plan says "user hive", which is wrong for this setting, so this needs your call | Medium |
| Background launcher demotion | process priority (temporary) | No: and the "known-safe" list needs `tweak-dictionary.md` (N2) | Medium, blocked on N2 |

Recommendation: ship the first two as Free tweaks first (small, fully journalled), then design the power-plan record kind. Each tweak gets: touches() allowlist, read_state with Drifted, tests on fake + real registry, a scanner finding that names it as `fixTweakId`, and evidence-grade text from the dictionary (N2).

### Step 4. UI build-out (can start with Step 1; most of it does not need new tweaks)

Current UI: Home (state sentence, restore step, last change, findings grouped by who can fix, printable), Games (main game, anti-cheat readiness, game cards with install location and in-game advice), Tools (catalogue, Advanced switch, acknowledge-tradeoff), Proof (sessions, capture, verdict), Backups (applied, restore points, journal, offline recovery), Settings (rig override, wording), Execution Bus. 4. **Auto mode button on Home** (plan 6.3: scan → restore point → apply the safe set for the rig class → re-check → result card). The flow can be built against the mock now; the "safe set" content needs N2. Medium.

6. **Starter mode** (plan 6.4): a simplified shell for parents and children (plain wording forced, no Advanced, five fixes, game cards, printable scan). Mostly hiding and re-arranging existing parts. Medium.
7. **Visual polish**: real icon and logo (N12, needs art), empty states, motion within reduced-motion rules. Small-medium.
8. **Later (Phase 6/7)**: game profile pages, licence/upgrade screens, update notice.

Each UI step: Playwright + axe in CI against the mock, and the real-app WebDriver test extended to cover it.
